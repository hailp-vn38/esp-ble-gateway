## V4-03: Replace `device_capabilities` with `device_schema`

### Overview

Replace the flat `device_capabilities` component (12 items/device) with `device_schema` supporting structured `tools[]` + `features[]`. The discovery transaction evolves to handle both tool items and feature items from the BLE device.

### Data Model Changes

**New types:**
- `device_schema_tool_t` — command, label, unit, value_type, flags, min/max/step (replaces `device_capability_t`)
- `device_schema_feature_t` — feature_id, feature_type, feature_schema_version, feature_flags, property_id, feature_value_bool/int, writable_tool_index
- `device_schema_snapshot_t` — tools[] + features[] instead of flat items[]

**Constants:** `DEVICE_SCHEMA_MAX_TOOLS=12`, `DEVICE_SCHEMA_MAX_FEATURES=12`

### Discovery Flow Changes

1. `capabilities_begin` → stores `total` (tool count) + `feature_total` (feature count)
2. `capability_item` → appends to `staging.tools[]` (same as before, just renamed)
3. `feature_item` (new message type) → appends to `staging.features[]`, validates feature_type/property/schema_version, resolves `writable_tool_index` by matching `feature_tool` command name against tools[]
4. `capabilities_end` → commits only when `tool_count == total && feature_count == feature_total`

### NVS Persistence

- New NVS namespace key format: `sch00`–`sch15` (avoids stale `cap00` data)
- Persisted blob stores both tools[] and features[]
- Schema version stays at 1 (compatible layout)

### Validation Logic

- `validate_command` searches `tools[]` instead of `items[]`
- Feature validation: duplicate feature_id rejection, writable_tool_index resolution
- Argument validation unchanged (value_type, min/max/step)

### Internal Renames

- All `CAP_*` constants → `SCHEMA_*`
- Log tag: `device_caps` → `device_schema`
- Worker queue depth, stack, priority unchanged
