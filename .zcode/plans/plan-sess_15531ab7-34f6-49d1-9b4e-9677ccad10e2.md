## G3 — Settings Worker and Coordinator

### Gap Analysis

The `device_settings` component has a documented but incomplete operation layer:
- `device_settings_operation.c` queues DESCRIBE/GET operations into a static `s_ops[]` array
- `device_settings_on_capability()` (G2) calls `describe()` or `get()` to queue
- **No worker thread exists** — queued operations are never submitted as BLE commands
- `device_settings_protocol.c` has `device_settings_get()` called directly from `handle_end()` — violates "READ only after DESCRIBE ACK"
- No BUSY retry, no disconnect cleanup for queued ops, no duplicate coalescing

### Architecture

A new `device_settings_worker.c` adds a FreeRTOS task that:
1. Polls `s_ops[]` for the first `QUEUED` operation
2. Submits a BLE command via `device_command_service_submit()` (`describe_settings` or `read_settings`)
3. Handles completion (ACK, BUSY, TIMEOUT, DISCONNECT) via command service callback
4. Enforces global serialization — one active settings stream at a time
5. Retries BUSY with bounded backoff (100ms → 250ms → 500ms → fail)
6. Cleans up on disconnect — cancels active command, increments generation, releases ownership
7. Coalesces duplicates — same device_id + operation kind + generation → skip

### Exit Gate

```
[ ] queued operations are actually transmitted
[ ] one global Settings stream owner
[ ] BUSY bounded retry implemented
[ ] READ starts only after DESCRIBE ACK
[ ] duplicate operations coalesced
[ ] disconnect releases ownership
```
